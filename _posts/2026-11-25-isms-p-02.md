## 01 온프레미스와 클라우드 {#section-01}

먼저 온프레미스와 클라우드 환경의 차이를 알아보겠습니다.

- **온프레미스(On-premises)**: 기업이 자체적으로 서버와 인프라를 구축하고 관리하는 방식
- **클라우드(Cloud)**: 클라우드 서비스 제공자의 인프라와 서비스를 이용하는 방식

| 구분 | 온프레미스 | 클라우드 |
| --- | --- | --- |
| 서버 | 기업이 직접 구축 | 클라우드 인프라 이용 |
| 물리적 장비 관리 | 기업 | 클라우드 업체 |
| 초기 구축 비용 | 상대적으로 높음 | 상대적으로 낮음 |
| 예시 | 기업 내부 서버실 | AWS, Azure, GCP |

클라우드 환경에서는 기업이 직접 서버실을 구축하고 물리적인 장비를 관리해야 하는 부담이 줄어듭니다.

이때 등장하는 개념이 **책임 공유 모델**입니다.

## 02 책임 공유 모델(Shared Responsibility Model) {#section-02}

클라우드 서비스 제공자와 이용자가 보안에 대한 책임을 나누어 가지는 모델입니다.

AWS와 같은 클라우드 서비스 제공자를 **CSP(Cloud Service Provider)**라고 부르는데요.

어떤 형태의 클라우드 서비스를 이용하느냐에 따라 보안 책임의 범위도 달라집니다.

| 관리 대상 | 온프레미스 | IaaS | PaaS | SaaS |
| --- | --- | --- | --- | --- |
| 물리적 서버 | 사용자 | 업체 | 업체 | 업체 |
| 네트워크 인프라 | 사용자 | 업체 | 업체 | 업체 |
| 운영체제 | 사용자 | 사용자 | 업체 | 업체 |
| 애플리케이션 | 사용자 | 사용자 | 사용자 | 업체 |
| 사용자 권한 및 데이터 관리 | 사용자 | 사용자 | 사용자 | 공동 |

※ 대표적인 책임 분담이며, 세부 범위는 이용하는 서비스에 따라 달라질 수 있습니다.

예를 들어 AWS EC2를 사용한다면 AWS는 데이터센터와 물리적 서버의 보안을 담당하고, 이용자는 운영체제, 애플리케이션, 접근 권한 등을 관리합니다.

## 03 클라우드 환경에서의 정보자산 {#section-03}

AWS 환경에서는 다음과 같은 리소스가 정보자산의 관리 대상이 될 수 있습니다.

| AWS 서비스 | 역할 | 보안 관리 항목 예시 |
| --- | --- | --- |
| EC2 | 가상 서버 | 운영체제, 접근 권한 |
| S3 | 객체 저장소 | 외부 공개 여부 |
| RDS | 관리형 데이터베이스 | 암호화, 백업 |
| EKS | 관리형 Kubernetes | 접근 권한 |
| Lambda | 서버리스 함수 실행 | 실행 권한 |

각 리소스의 역할과 특성에 맞는 보안 정책을 적용해야 합니다.

## 04 인증 및 권한 관리 {#section-04}

### 04-1 AWS IAM {#section-04-1}

AWS에서 사용자와 리소스의 접근 권한을 관리하는 서비스입니다.

예를 들어 직원의 역할에 따라 다음과 같이 권한을 다르게 부여할 수 있습니다.

| 사용자 | 권한 예시 |
| --- | --- |
| 관리자 | 리소스 관리 |
| 개발자 | 개발 환경 리소스 이용 |
| 보안 담당자 | 로그 및 보안 설정 확인 |

지난 글에서 설명한 최소 권한 원칙을 실제 AWS 환경에 적용하는 대표적인 서비스입니다.

### 04-2 Keycloak {#section-04-2}

Keycloak은 사용자 인증 및 권한 관리를 지원하는 오픈소스 IAM 솔루션입니다.

기업에서 여러 업무 시스템을 운영하는 경우, 시스템마다 계정을 생성하고 관리하면 번거롭겠죠?

Keycloak을 활용하면 사용자 인증을 중앙에서 관리할 수 있습니다.

### 04-3 SSO와 SAML {#section-04-3}

- **SSO(Single Sign-On)**는 한 번 로그인한 후 연동된 여러 서비스에 접근할 수 있도록 하는 방식입니다.

학교 통합 계정으로 포털, 수강신청 등의 서비스에 접근하는 것을 생각하시면 이해하기 쉽습니다.

- **SAML(Security Assertion Markup Language)**은 시스템 간 인증 정보를 교환하기 위한 표준입니다.

| 용어 | 설명 |
| --- | --- |
| IdP (Identity Provider) | 사용자의 신원을 확인하는 시스템 |
| SP (Service Provider) | 사용자에게 서비스를 제공하는 시스템 |
| SAML | 시스템 간 인증 정보를 전달하는 표준 |

Keycloak이 IdP 역할을 하고 AWS가 SP 역할을 하는 방식으로 연동할 수 있습니다.

## 05 데이터 암호화 {#section-05}

### 05-1 AWS KMS {#section-05-1}

- **Key Management Service (암호화 키 관리 서비스)**의 약자입니다.

데이터를 암호화할 때 사용되는 암호화 키를 생성하고 관리하는 서비스입니다.

데이터를 암호화하더라도 복호화에 사용되는 키가 안전하게 관리되지 않으면 보안 문제가 발생할 수 있는데요.

KMS를 이용하면 암호화 키의 접근 권한과 사용 기록 등을 관리할 수 있습니다.

## 06 네트워크 접근 통제 {#section-06}

### 06-1 VPC {#section-06-1}

**Virtual Private Cloud**의 약자로, AWS에서 논리적으로 분리된 가상 네트워크를 구성하는 서비스입니다.

AWS에서는 이러한 네트워크의 접근을 통제하기 위해 **NACL**과 **Security Group**을 사용할 수 있습니다.

| 구분 | NACL | Security Group |
| --- | --- | --- |
| 적용 범위 | 서브넷 | 네트워크 인터페이스 |
| 동작 방식 | Stateless | Stateful |
| 규칙 | Allow, Deny | Allow |
| 역할 | 네트워크 구역 접근 통제 | 개별 리소스 접근 통제 |

여기서 중요한 차이는 **Stateful과 Stateless**입니다.

- **Stateful**: 허용된 요청에 대한 응답 트래픽을 자동으로 허용합니다.
- **Stateless**: 요청과 응답 트래픽을 각각 독립적으로 검사합니다.

Security Group은 Stateful 방식이고, NACL은 Stateless 방식입니다.

## 07 로그 관리 및 모니터링 {#section-07}

### 07-1 AWS CloudTrail {#section-07-1}

AWS에서 발생하는 API 활동 등의 기록을 남기는 서비스입니다.

다음과 같은 정보를 확인할 수 있습니다.

- 누가 AWS 관리자 콘솔에 로그인했는가?
- 누가 리소스를 생성하거나 삭제했는가?
- 누가 보안 설정을 변경했는가?
- 언제 해당 작업이 발생했는가?

이처럼 사용자의 활동을 추적할 수 있는 특성을 **책임추적성(Accountability)**이라고 합니다.

보안 사고가 발생했을 때 원인을 분석하는 데 활용할 수 있습니다.

### 07-2 Amazon CloudWatch {#section-07-2}

AWS 리소스와 애플리케이션의 상태를 모니터링하는 서비스입니다.

CPU 사용량, 로그, 시스템 오류 등의 정보를 확인할 수 있으며, 특정 조건에 따라 알림을 설정할 수도 있습니다.

## 08 보안 설정 및 취약점 점검 {#section-08}

### 08-1 AWS Config {#section-08-1}

AWS 리소스의 설정 상태와 변경 이력을 확인하고, 설정이 지정된 규칙을 준수하는지 평가하는 서비스입니다.

예를 들어 기업의 보안 정책으로 고객정보가 저장된 S3 버킷의 외부 공개를 제한할 수 있습니다.

AWS Config에 관련 규칙을 설정하면 리소스의 설정이 해당 규칙을 준수하는지 평가할 수 있습니다.

### 08-2 AWS Trusted Advisor {#section-08-2}

AWS 리소스의 구성을 모범 사례에 따라 점검하고 개선 사항을 제안하는 서비스입니다.

보안뿐만 아니라 비용 최적화, 성능, 서비스 사용 한도 등의 항목도 확인할 수 있습니다.

### 08-3 Amazon Inspector {#section-08-3}

AWS 환경에서 자동화된 취약점 점검을 수행하는 서비스입니다.

EC2, ECR 컨테이너 이미지, Lambda 등에서 지원 대상 소프트웨어의 보안 취약점을 확인할 수 있습니다.

취약점 점검은 발견 이후 수정하고, 조치 결과를 확인하는 과정까지 이어져야 합니다.

## 09 AWS 보안 서비스 한눈에 정리 {#section-09}

ISMS-P의 보호대책 요구사항과 앞에서 살펴본 AWS 서비스를 연결해 정리해보겠습니다.

| 보호대책 | 관련 서비스 | 역할 |
| --- | --- | --- |
| 인증 및 권한 관리 | IAM | 사용자 및 접근 권한 관리 |
| 접근 통제 | NACL, Security Group | 네트워크 접근 제한 |
| 암호화 적용 | KMS | 암호화 키 관리 |
| 로그 관리 | CloudTrail | 사용자 및 API 활동 기록 |
| 시스템 운영관리 | CloudWatch | 리소스 상태 모니터링 |
| 보안 설정 관리 | AWS Config | 설정 변경 이력 및 규칙 준수 확인 |
| 보안 구성 점검 | Trusted Advisor | 모범 사례 기반 개선 사항 제안 |
| 취약점 점검 | Amazon Inspector | 소프트웨어 취약점 확인 |

이러한 서비스를 활용하면 ISMS-P의 여러 보호대책 요구사항을 충족하는 데 도움을 받을 수 있습니다.

## 10 마무리 {#section-10}

1편에서는 ISMS-P의 관리 기준을, 2편에서는 이러한 기준을 클라우드 환경에 적용하는 방법을 알아봤습니다.

클라우드 환경에서는 책임 공유 모델을 이해하고, 각 서비스의 역할과 기업의 보안 정책에 맞게 보안 기능을 적용하는 것이 중요합니다.
